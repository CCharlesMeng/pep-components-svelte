# pep-debug (Architect Grade)

## 🎯 核心使命
不仅是修复 Bug，更是通过“诊断-修复-审计-沉淀”四部曲，确保同类 Bug 在 100+ 组件中彻底绝迹。

## 🛠 严格执行协议

### Phase 1: 深度诊断 (Deep Diagnosis)
1. **复现确认**：执行相关的测试或构建命令，**必须首先观察到失败**。禁止在未复现的情况下尝试修复。
2. **知识对齐**：
    - 读取 `.cursor/debug-solutions/project/global.md`。
    - **强制动作**：搜索整个 `.cursor/debug-solutions/` 目录，寻找关键词匹配。
3. **上下文分析**：分析受影响组件是否引用了 `shared/` 目录下的原子组件，如果是，优先怀疑原子组件。

### Phase 2: 原子修复 (Atomic Fix)
1. **最小方案**：提出仅针对根因的最小改动。禁止大面积重构。
2. **回滚点标记**：在修改前记录当前 git 状态或文件快照。如果修复后测试仍失败，**必须立即撤销修改**，重新诊断。
3. **双重验证**：
    - 验证修复后的代码通过了之前失败的测试。
    - 验证受影响组件的邻近功能（Regression Check）未受损。

### Phase 3: 横向审计 (Proactive Audit) - 核心加固
1. **模式搜索**：使用 `grep` 或 `codebase_search` 在全仓库搜索刚修复的“错误代码模式”。
2. **风险报告**：如果发现其他组件存在同类隐患，必须在输出中明确列出：“发现 X, Y, Z 组件也存在类似风险，建议同步修复”。

### Phase 4: 知识沉淀 (Knowledge Hardening)
1. **价值判别准则**：
    - **Global**：涉及工具链、`shared/` 逻辑、多组件通用的 CSS/JS 模式、Svelte 底层陷阱。
    - **Component**：仅涉及该组件特有的业务逻辑、Schema 字段。
2. **结构化写入**：
    - 必须包含：[问题类型] [影响范围] [错误模式] [修复方案] [审计关键词]。
    - **审计关键词**：提供一个 `grep` 命令，用于未来快速检测此类问题。

## ⚠️ 严禁行为
- 严禁在测试失败时直接写入知识库。
- 严禁在未确认横向影响的情况下关闭 Debug 任务。
- 严禁删除知识库中的历史诊断轨迹。
