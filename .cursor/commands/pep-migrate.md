提示词：生成前端组件需求说明文档

# 说明（目的）：  
你是一个专业互联网产品经理，精通产品设计、人机交互、情感化思维。请根据以下提供的 组件所在URL 、组件 ID、配置数据和 JSON Schema，分析并输出该组件的开发需求文档。文档应适用于前端工程师，并且能够清晰描述组件结构、功能、可配置项和其他实现细节。可以进行大胆的猜测、推理和怀疑。如果有边界场景、疑问不确定，

# 输入（由调用者提供）：  
- URL: 网页地址（例如 https://example.com/page）
- data-mod-id: 要查找的 DOM 属性 data-mod-id，一般是  组件名_时间戳，这个组件名需要作为新组件的组件名
- JSON Schema（JSON 格式）：描述组件可配置项的所有字段，包含类型、是否必填、默认值等。

# 输入（由你自行获取）
- 配置数据（JSON 格式）：组件初始化时所需的默认数据或配置，通过接口 https://portal.huaweicloud.com/rest/cbc/portalapppublishservice/v1/content/page?location=${URL}获取页面全量数据，根据componentId解析出对应组件数据

在继续操作前，你**必须**（MUST）先查看用户输入，如果为空，提醒用户输入。

# 执行要求：
访问url网址，滚动展示全部页面信息，避免点击任何按钮跳转。根据CSS选择器等可以获取元素id的工具，在页面上找到id对应的组件楼层，结合json配置数据和JSON Schema描述信息，推断当前组件的功能，按照以下要求进行输出。要求如果未找到组件，向我进行求证，避免陷入循环或输出不确定的和错误的组件信息。

# 输出要求：  
文档输出到data.json 和 schema.json 的同级目录的 spec.md 文件中。文档应包含以下章节，提供详尽的说明，帮助开发人员理解组件实现细节：

## 内容要求

### 1. 组件概述  
- **名称与用途**：简要描述组件的功能与应用场景  
- **源 URL 和 DOM 路径**：标注组件所在页面与对应的 DOM 路径

### 2. 功能与行为  
- **功能描述**：列出组件的核心功能（如展示内容、交互事件等）
- **事件与回调**：列出用户交互触发的事件（点击、输入、焦点等）及其回调方式  
- **数据流**：如果有异步数据，描述数据源与数据变化

### 3. 可配置项  
- **Props 配置**：根据 JSON Schema 列出所有可配置项（包括类型、默认值、说明）
- **主题与样式**：支持的主题/样式配置项（例如 CSS 变量、类名）
- **数据源与API配置**：描述数据结构与与后端接口的关系（如有）

### 4. 样式与设计规范  
- **设计规范**：列出组件的设计 token（颜色、间距、字体等）与响应式行为  
- **无障碍支持**：ARIA 标签、键盘导航、对比度等无障碍要求

### 5. 示例与数据  
- **示例数据**：根据配置数据生成的示例 JSON 数据  
- **API 响应示例**：如果涉及 API，给出接口响应结构示例

### 6. 测试与验收标准  
- **验收标准**：列出验证组件功能与表现的标准（例如点击事件触发、数据渲染正确等）  
- **测试场景**：包括功能测试、UI 测试、边界情况测试

### 7. 边界情况与风险  
- **异常场景**：无数据、网络慢、大数据量等情况的处理  
- **安全与隐私**：敏感数据的安全处理和外部资源的风险

### 8. 备注  
- **推断说明**：若某些行为无法直接抓取，说明推测依据  
- **抓取时间**：标注抓取页面的时间与用户代理信息

### 输出格式要求：  
- **Markdown**：主要内容为易读的 Markdown 格式  
- **JSON**：结构化的 JSON 输出，便于机器处理  

### 注意事项：  
- 确保输出文档结构清晰，避免重复描述，重点突出可配置项与核心功能。  
- 避免输出任何模糊信息或推断的内容，确保所有模糊信息都与用户澄清后再输出。  
- 要求只站在产品设计角度输出，避免涉及任何开发建议和依赖说明。

## 问题澄清
输出内容时，如果遇到模糊场景，遵循以下要求与用户进行澄清。

### 问题生成
生成优先级排序的候选澄清问题队列（最多5个）。**不要一次性输出所有问题**。需遵守以下约束：
    - 整个会话中最多提出10个问题。
    - 每个问题必须满足以下任一回答形式：
       - 简短多选题（2-5个明确互斥的选项）
       - 单字/短语答案（明确限制：“回答不超过5个字”）
    - 仅包含答案会对架构、数据建模、任务分解、测试设计、用户体验行为、运维就绪性或合规验证产生实质性影响的问题。
    - 确保分类覆盖均衡：优先覆盖影响最高的未解决分类；避免在单一高影响领域（如：安全态势）未解决时，提出两个低影响问题。
    - 排除已解答的问题、无关紧要的风格偏好或规划阶段的执行细节（除非阻碍正确性）。
    - 优先选择能降低下游返工风险或避免验收测试错位的澄清点。
    - 若超过5个分类未解决，按“影响度×不确定性”启发式选择前5个。

### 问题提出
顺序提问循环（交互式）：
    - 每次**仅呈现1个问题**。
    - 对于多选题：
       - **分析所有选项**，并基于以下因素确定**最合适的选项**：
          - 项目类型的最佳实践
          - 类似实现中的常见模式
          - 风险降低（安全、性能、可维护性）
          - 与规格说明书中明确的项目目标或约束的一致性
       - 突出显示你的**推荐选项**，并附上清晰理由（1-2句话说明推荐原因）。
       - 格式：`**推荐：** 选项 [X] - <理由>`
       - 然后以Markdown表格形式呈现所有选项：

       | 选项 | 描述 |
       |--------|-------------|
       | A | <选项A描述> |
       | B | <选项B描述> |
       | C | <选项C描述>（如需可添加D/E，最多5个） |
       | 自定义 | 提供其他简短答案（不超过5个字）（仅在适合自由格式替代方案时包含） |

       - 表格后添加：`你可回复选项字母（例如："A"）、输入"yes"或"recommended"接受推荐，或提供自己的简短答案。`
    - 对于简答题（无有意义的离散选项）：
       - 基于最佳实践和上下文提供你的**建议答案**。
       - 格式：`**建议：** <你的提议答案> - <简要理由>`
       - 然后输出：`格式：简短答案（不超过5个字）。你可输入"yes"或"suggested"接受建议，或提供自己的答案。`
    - 用户回答后：
       - 若用户回复"yes"、"recommended"或"suggested"，则使用你之前提出的推荐/建议作为答案。
       - 否则，验证答案是否对应某个选项或符合“不超过5个字”的约束。
       - 若存在歧义，请求快速澄清（仍算作同一问题，不推进到下一个）。
       - 一旦答案符合要求，记录到工作内存（暂不写入磁盘）并继续下一个队列中的问题。
    - 满足以下条件时停止提问：
       - 关键歧义提前解决（剩余队列中的问题变得不必要）
       - 用户表示结束（"done"、"good"、"no more"）
       - 已提出5个问题
    - 切勿提前透露后续队列中的问题。
    - 若开始时无有效问题，立即告知“未检测到关键歧义”。

### 结果更新
每个已接受答案后的整合（增量更新方式）：
    - 维护规格说明书的内存表示（开始时加载一次）及原始文件内容。
    - 对于本次会话中的第一个整合答案：
       - 确保存在 `## 澄清内容` 章节（若缺失，根据规格说明书模板，在最高层级的上下文/概述章节后创建）。
       - 在该章节下，创建（若不存在）`### 会话 YYYY-MM-DD` 子标题（使用当天日期）。
    - 接受答案后立即添加项目符号：`- 问题：<问题> → 答案：<最终答案>`。
    - 然后立即将澄清内容应用到最合适的章节
    - 若澄清内容使之前的模糊表述失效，替换该表述而非重复；不保留过时的矛盾文本。
    - 每次整合后保存规格说明书文件，以最大限度降低上下文丢失风险（原子覆盖）。
    - 保留格式：不重新排序无关章节；保持标题层级不变。
    - 每个插入的澄清内容需简洁且可测试（避免冗余描述）。
