## 用户输入

```text
$ARGUMENTS
```

在继续之前，你**必须**考虑用户输入（若不为空）。

## 大纲

目标：识别并减少当前功能规格说明书中的歧义或缺失的决策点，并将澄清内容直接记录到规格说明书文件中。

注意：此澄清工作流需在调用 `/speckit.plan` **之前** 执行（并完成）。若用户明确表示跳过澄清（例如：探索性研究），你可继续执行，但必须警告下游返工风险会增加。

执行步骤：

1. 从代码库根目录**执行一次** `{SCRIPT}`（启用 `--json --仅输出路径` 合并模式 / `-Json -仅输出路径`）。解析最小化JSON负载字段：
   - `FEATURE_DIR`（功能目录）
   - `FEATURE_SPEC`（功能规格说明书路径）
   - （可选捕获 `IMPL_PLAN`（实现方案）、`TASKS`（任务），用于后续链式流程。）
   - 若JSON解析失败，终止流程并告知用户重新运行 `/speckit.specify` 或验证功能分支环境。
   - 对于参数中包含单引号的情况（如 "I'm Groot"），使用转义语法：例如 'I'\''m Groot'（或尽可能使用双引号："I'm Groot"）。

2. 加载当前规格说明书文件。使用以下分类体系执行结构化歧义与覆盖度扫描。为每个分类标记状态：清晰（Clear）/ 部分明确（Partial）/ 缺失（Missing）。生成用于优先级排序的内部覆盖度地图（除非不打算提出任何问题，否则不输出原始地图）。

   功能范围与行为：
   - 核心用户目标与成功标准
   - 明确的范围外声明
   - 用户角色/人物画像区分

   领域与数据模型：
   - 实体、属性、关系
   - 标识与唯一性规则
   - 生命周期/状态转换
   - 数据量/规模假设

   交互与用户体验流程：
   - 关键用户旅程/流程序列
   - 错误/空数据/加载状态
   - 可访问性或本地化说明

   非功能质量属性：
   - 性能（延迟、吞吐量目标）
   - 可扩展性（水平/垂直扩展、限制）
   - 可靠性与可用性（ uptime、恢复预期）
   - 可观测性（日志、指标、追踪信号）
   - 安全性与隐私（身份认证/授权、数据保护、威胁假设）
   - 合规性/监管约束（如有）

   集成与外部依赖：
   - 外部服务/API及故障模式
   - 数据导入/导出格式
   - 协议/版本假设

   边界情况与故障处理：
   - 异常场景（负面场景）
   - 限流/节流机制
   - 冲突解决（例如：并发编辑）

   约束与权衡：
   - 技术约束（语言、存储、部署环境）
   - 明确的权衡或被否决的替代方案

   术语与一致性：
   - 规范术语表
   - 禁用同义词/废弃术语

   完成信号：
   - 验收标准可测试性
   - 可量化的“完成定义”类指标

   其他/占位符：
   - TODO标记/未解决的决策
   - 缺乏量化的模糊形容词（如“健壮的”、“直观的”）

   对于每个状态为“部分明确”或“缺失”的分类，添加候选问题（除非满足以下条件）：
   - 澄清内容不会对实现或验证策略产生实质性影响
   - 信息更适合推迟到规划阶段（内部记录）

3. （内部）生成优先级排序的候选澄清问题队列（最多5个）。**不要一次性输出所有问题**。需遵守以下约束：
    - 整个会话中最多提出10个问题。
    - 每个问题必须满足以下任一回答形式：
       - 简短多选题（2-5个明确互斥的选项）
       - 单字/短语答案（明确限制：“回答不超过5个字”）
    - 仅包含答案会对架构、数据建模、任务分解、测试设计、用户体验行为、运维就绪性或合规验证产生实质性影响的问题。
    - 确保分类覆盖均衡：优先覆盖影响最高的未解决分类；避免在单一高影响领域（如：安全态势）未解决时，提出两个低影响问题。
    - 排除已解答的问题、无关紧要的风格偏好或规划阶段的执行细节（除非阻碍正确性）。
    - 优先选择能降低下游返工风险或避免验收测试错位的澄清点。
    - 若超过5个分类未解决，按“影响度×不确定性”启发式选择前5个。

4. 顺序提问循环（交互式）：
    - 每次**仅呈现1个问题**。
    - 对于多选题：
       - **分析所有选项**，并基于以下因素确定**最合适的选项**：
          - 项目类型的最佳实践
          - 类似实现中的常见模式
          - 风险降低（安全、性能、可维护性）
          - 与规格说明书中明确的项目目标或约束的一致性
       - 突出显示你的**推荐选项**，并附上清晰理由（1-2句话说明推荐原因）。
       - 格式：`**推荐：** 选项 [X] - <理由>`
       - 然后以Markdown表格形式呈现所有选项：

       | 选项 | 描述 |
       |--------|-------------|
       | A | <选项A描述> |
       | B | <选项B描述> |
       | C | <选项C描述>（如需可添加D/E，最多5个） |
       | 自定义 | 提供其他简短答案（不超过5个字）（仅在适合自由格式替代方案时包含） |

       - 表格后添加：`你可回复选项字母（例如："A"）、输入"yes"或"recommended"接受推荐，或提供自己的简短答案。`
    - 对于简答题（无有意义的离散选项）：
       - 基于最佳实践和上下文提供你的**建议答案**。
       - 格式：`**建议：** <你的提议答案> - <简要理由>`
       - 然后输出：`格式：简短答案（不超过5个字）。你可输入"yes"或"suggested"接受建议，或提供自己的答案。`
    - 用户回答后：
       - 若用户回复"yes"、"recommended"或"suggested"，则使用你之前提出的推荐/建议作为答案。
       - 否则，验证答案是否对应某个选项或符合“不超过5个字”的约束。
       - 若存在歧义，请求快速澄清（仍算作同一问题，不推进到下一个）。
       - 一旦答案符合要求，记录到工作内存（暂不写入磁盘）并继续下一个队列中的问题。
    - 满足以下条件时停止提问：
       - 关键歧义提前解决（剩余队列中的问题变得不必要）
       - 用户表示结束（"done"、"good"、"no more"）
       - 已提出5个问题
    - 切勿提前透露后续队列中的问题。
    - 若开始时无有效问题，立即告知“未检测到关键歧义”。

5. 每个已接受答案后的整合（增量更新方式）：
    - 维护规格说明书的内存表示（开始时加载一次）及原始文件内容。
    - 对于本次会话中的第一个整合答案：
       - 确保存在 `## 澄清内容` 章节（若缺失，根据规格说明书模板，在最高层级的上下文/概述章节后创建）。
       - 在该章节下，创建（若不存在）`### 会话 YYYY-MM-DD` 子标题（使用当天日期）。
    - 接受答案后立即添加项目符号：`- 问题：<问题> → 答案：<最终答案>`。
    - 然后立即将澄清内容应用到最合适的章节：
       - 功能歧义 → 在“功能需求”中更新或添加项目符号。
       - 用户交互/角色区分 → 在“用户故事”或“角色”子章节（如有）中更新澄清后的角色、约束或场景。
       - 数据结构/实体 → 在“数据模型”中更新（添加字段、类型、关系），保持原有顺序；简洁记录新增约束。
       - 非功能约束 → 在“非功能/质量属性”章节中添加/修改可量化标准（将模糊形容词转换为指标或明确目标）。
       - 边界情况/异常流程 → 在“边界情况/错误处理”下添加新项目符号（或在模板提供占位符时创建该子章节）。
       - 术语冲突 → 统一规格说明书中的术语；如需保留原始术语，仅添加一次 `（原称为"X"）`。
    - 若澄清内容使之前的模糊表述失效，替换该表述而非重复；不保留过时的矛盾文本。
    - 每次整合后保存规格说明书文件，以最大限度降低上下文丢失风险（原子覆盖）。
    - 保留格式：不重新排序无关章节；保持标题层级不变。
    - 每个插入的澄清内容需简洁且可测试（避免冗余描述）。

6. 验证（每次写入后及最终检查）：
   - 澄清会话中每个已接受答案对应一个项目符号（无重复）。
   - 已提出（已接受）的问题总数 ≤ 5。
   - 更新后的章节中无该答案本应解决的残留模糊占位符。
   - 无残留的矛盾早期表述（扫描并移除现已失效的替代选项）。
   - Markdown结构有效；仅允许新增标题：`## 澄清内容`、`### 会话 YYYY-MM-DD`。
   - 术语一致性：所有更新章节中使用相同的规范术语。

7. 将更新后的规格说明书写回 `FEATURE_SPEC` 路径。

8. 完成报告（提问循环结束或提前终止后）：
   - 已提出及已解答的问题数量。
   - 更新后的规格说明书路径。
   - 受影响的章节（列出名称）。
   - 覆盖度摘要表：列出每个分类体系的状态（已解决：原部分明确/缺失且已处理；推迟：超出问题配额或更适合规划阶段；清晰：原本已足够；未解决：仍部分明确/缺失但影响较低）。
   - 若存在未解决或推迟的高影响分类，明确建议是否继续执行 `/speckit.plan` 或后续再次运行 `/speckit.clarify`。
   - 建议的下一步命令。

行为规则：
- 若未发现有意义的歧义（或所有潜在问题均为低影响），回复：“未检测到需正式澄清的关键歧义。” 并建议继续执行后续步骤。
- 若规格说明书文件缺失，告知用户先运行 `/speckit.specify`（不在此处创建新规格说明书）。
- 最多提出5个问题（单个问题的澄清重试不计入新问题）。
- 除非缺失的技术栈信息阻碍功能清晰度，否则避免提出推测性技术栈问题。
- 尊重用户的提前终止信号（"stop"、"done"、"proceed"）。
- 若因覆盖度完整而未提出任何问题，输出简洁的覆盖度摘要（所有分类均为“清晰”）并建议推进。
- 若问题配额用尽但仍有未解决的高影响分类，明确标记这些分类为“推迟”并说明理由。
