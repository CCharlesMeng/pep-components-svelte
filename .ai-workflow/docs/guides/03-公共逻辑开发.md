# Monorepo公共逻辑开发指南

本指南说明如何在Monorepo根目录开发公共代码、配置、工具等所有组件共享的内容。

---

## 🎯 什么是公共逻辑？

在Monorepo中，公共逻辑是指**所有组件共享**的代码和配置：

### 典型公共逻辑

```
pep-components-svelte/
├── packages/
│   ├── shared-utils/          # 🔧 公共工具函数
│   ├── shared-types/          # 📘 公共TypeScript类型
│   ├── shared-styles/         # 🎨 公共样式和主题
│   └── shared-icons/          # 🎭 公共图标库
│
├── configs/
│   ├── tsconfig.base.json     # ⚙️  TypeScript基础配置
│   ├── vite.config.base.js    # ⚙️  Vite基础配置
│   └── eslint.config.js       # ⚙️  ESLint配置
│
├── scripts/
│   ├── build-all.sh           # 🔨 构建脚本
│   └── test-all.sh            # ✅ 测试脚本
│
├── global-rules.json          # 📋 全局规则定义
├── pnpm-workspace.yaml        # 📦 Workspace配置
└── package.json               # 📦 根package.json
```

## 🚀 开发流程

### 方案1: 标准项目模式（推荐）

公共逻辑通常作为独立的**标准项目**来管理，而不是单个组件。

#### 步骤1: 初始化公共包

```bash
# 在monorepo根目录
cd /path/to/pep-components-svelte

# 创建公共包目录
mkdir -p packages/shared-utils

# 初始化为标准项目
cd packages/shared-utils
python3 ../../cursor-autonomous-coding/scripts/init-project.js \
  --spec spec.md

# 生成文件：
# ✅ features.json
# ✅ DEVELOPMENT.md
# ✅ .cursor-dev/
```

编辑 `packages/shared-utils/features.json`:

#### 步骤3: 使用标准工作流

```bash
# 进入公共包目录
cd packages/shared-utils

# 获取任务（不需要 --component 参数）
python3 ../../cursor-autonomous-coding/scripts/next-task.js --save

# 复制提示词到Cursor，开始开发

# 完成后标记
python3 ../../cursor-autonomous-coding/scripts/mark-done.js --feature-id 1

# 提交代码
git add packages/shared-utils/
git commit -m "feat(shared-utils): 实现字符串工具函数"

# 查看进度
python3 ../../cursor-autonomous-coding/scripts/report.js
```

### 方案2: Monorepo组件模式

如果你希望将公共逻辑也作为"组件"管理，可以：

```bash
# 在components/目录下创建公共包
mkdir -p components/_shared-utils

# 作为组件初始化
node scripts/init-component.js \
  --component _shared-utils

# 使用组件模式的命令
node scripts/next-task.js --component _shared-utils --save
node scripts/mark-done.js --component _shared-utils --feature-id 1
```

**命名建议**: 使用 `_` 前缀区分公共包和普通组件（如 `_shared-utils`）

### 在组件中使用

```json

{

  "dependencies": {
    "@pep/shared-utils": "workspace:*",  // 依赖公共包

  }

```

```typescript

<script lang="ts">
  import { capitalizeFirst } from '@pep/shared-utils';
  import { theme } from '@pep/shared-styles';

  $: displayTitle = capitalizeFirst(title);

```

## ⚙️  全局配置文件

### TypeScript配置

```
configs/
├── tsconfig.base.json      # 基础配置（所有项目继承）
├── tsconfig.component.json # 组件配置模板
└── tsconfig.lib.json       # 库配置模板
```

**tsconfig.base.json**:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "resolveJsonModule": true,
    "paths": {
      "@pep/*": ["./packages/*/src"]
    }
  }
}
```

**组件中继承**:

```json
// components/pep-button/tsconfig.json
{
  "extends": "../../configs/tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist"
  },
  "include": ["src"]
}
```

### 如何管理配置文件？

配置文件通常**不需要**使用features.json，因为：
- 🔧 配置文件变更较少
- 📝 直接编辑更方便
- ✅ 通过Git追踪即可

但如果配置很复杂，可以创建 `configs/features.json`:

```json
{
  "project": {
    "name": "monorepo-configs",
    "description": "Monorepo全局配置"
  },
  "features": [
    {
      "id": 1,
      "name": "统一TypeScript配置",
      "description": "创建tsconfig.base.json供所有包继承",
      "status": "completed"
    },
    {
      "id": 2,
      "name": "统一ESLint配置",
      "description": "创建eslint.config.js并配置规则",
      "status": "pending"
    }
  ]
}
```

用于定义所有组件必须遵循的规范：

```json

  "naming": {

    "src/index.ts"
```

## 🔨 公共构建脚本

### scripts/build-all.sh

```bash
#!/bin/bash

echo "🔨 构建所有公共包..."

# 构建顺序很重要！先构建被依赖的包
pnpm --filter @pep/shared-types build
pnpm --filter @pep/shared-utils build
pnpm --filter @pep/shared-styles build
pnpm --filter @pep/shared-icons build

echo "✅ 所有公共包构建完成"

echo "🔨 构建所有组件..."
pnpm --filter "pep-*" --parallel build

echo "✅ 构建完成！"
```

### scripts/test-all.sh

```bash
#!/bin/bash

echo "✅ 测试所有公共包..."
pnpm --filter "./packages/*" test

echo "✅ 测试所有组件..."
pnpm --filter "./components/*" test

echo "✅ 所有测试通过！"
```

### 使用脚本

```bash
# 构建所有
bash scripts/build-all.sh

# 测试所有
bash scripts/test-all.sh
```

## 🎯 开发公共逻辑的最佳实践

### 1. 包命名规范

```
✅ 好的命名:
@pep/shared-utils
@pep/shared-types
@pep/shared-styles

❌ 避免:
utils (太通用)
pep-utils (与组件命名冲突)
```

### 2. 版本管理

```json
// 使用workspace协议
{
  "dependencies": {
    "@pep/shared-utils": "workspace:*"  // 永远使用最新的workspace版本
  }
}
```

### 3. 导出规范

```typescript
// packages/shared-utils/src/index.ts

// ✅ 分类导出
export * from './string';
export * from './date';
export * from './validation';

// ✅ 提供子路径导出
// package.json exports:
{
  ".": "./dist/index.js",
  "./string": "./dist/string.js"  // 允许按需导入
}
```

### 4. 文档要求

每个公共包必须有清晰的README：

```markdown
# @pep/shared-utils

所有组件共享的工具函数库。

## 安装

\`\`\`bash
pnpm add @pep/shared-utils
\`\`\`

## 使用

\`\`\`typescript
import { capitalizeFirst, formatDate } from '@pep/shared-utils';

// 或按需导入
import { capitalizeFirst } from '@pep/shared-utils/string';
\`\`\`

## API

### 字符串工具

#### `capitalizeFirst(str: string): string`
将字符串首字母大写。

#### `truncate(str: string, length: number): string`
截断字符串到指定长度。

...
```

### 5. 测试覆盖

公共包必须有高测试覆盖率：

```typescript
// packages/shared-utils/src/string.test.ts
import { describe, it, expect } from 'vitest';
import { capitalizeFirst, truncate } from './string';

describe('capitalizeFirst', () => {
  it('应该将首字母大写', () => {
    expect(capitalizeFirst('hello')).toBe('Hello');
  });

  it('应该处理空字符串', () => {
    expect(capitalizeFirst('')).toBe('');
  });
});
```

要求：
- ✅ 单元测试覆盖率 > 80%
- ✅ 测试边界情况
- ✅ 测试错误处理

## 🐛 常见问题

### Q1: 公共包和组件有什么区别？

| 维度 | 公共包 | 组件 |
|------|--------|------|
| **位置** | `packages/` | `components/` |
| **用途** | 被其他包依赖 | 最终产物 |
| **命名** | `@pep/shared-*` | `pep-*` |
| **开发模式** | 标准项目模式 | 组件模式 |

### Q2: 公共包改了，组件需要做什么？

```bash
# 1. 更新依赖
pnpm install

# 2. 重新构建公共包
pnpm --filter @pep/shared-utils build

# 3. 重新构建使用该公共包的组件
pnpm --filter pep-button build
```

### Q3: 如何避免循环依赖？

```
✅ 正确的依赖方向:
组件 → 公共包
公共包之间也要注意依赖层级

❌ 避免:
公共包 → 组件
公共包A → 公共包B → 公共包A
```

### Q4: 公共逻辑要不要用features.json？

**推荐使用**，因为：
- ✅ 统一的开发流程
- ✅ 可追踪进度
- ✅ 自动生成提示词

但对于**简单配置文件**，可以不用。

## 🎉 总结

公共逻辑开发的关键点：

1. **📦 包结构** - 放在 `packages/` 目录，使用 `@pep/shared-*` 命名
2. **🔧 开发模式** - 使用标准项目模式（非组件模式）
3. **📝 功能清单** - 复杂公共包使用 features.json 管理
4. **✅ 测试覆盖** - 公共包必须有高测试覆盖率
5. **📖 文档完善** - 清晰的README和API文档
6. **🔄 更新流程** - 更新后通知相关组件重新构建
