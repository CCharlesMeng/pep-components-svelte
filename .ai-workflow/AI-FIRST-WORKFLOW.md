# PEP 组件 AI-First 开发流程

## 🎯 设计理念

基于 Claude Autonomous Coding 的核心思想，为 Cursor IDE 重新设计的 AI 驱动开发流程。

### 核心原则

1. **AI-First**: AI 是第一驱动力，脚本提供后端支持
2. **Spec-Driven**: 规格说明驱动任务生成和开发
3. **State-Aware**: 智能检测状态，避免混乱
4. **Automated Testing**: 集成 Puppeteer MCP 自动化测试
5. **Monorepo Friendly**: 原生支持多组件仓库

## 🎭 与 Claude Autonomous Coding 的对比

### 相同的核心思想

1. **任务驱动**: features.json 是唯一真相来源
2. **增量开发**: 一次一个任务，逐步推进
3. **自动归档**: 完成的任务自动归档
4. **Git 集成**: 每个任务对应一个 commit
5. **自动化测试**: 集成浏览器自动化测试

### 不同的实现方式

| 维度 | Claude | Cursor (PEP) |
|------|--------|--------------|
| **驱动方式** | Agent 自主循环 | AI Commands + 人工触发 |
| **交互方式** | 完全自动 | 交互式（AI + 人）|
| **规格输入** | app_spec.txt（预定义）| spec.md（渐进式）|
| **任务生成** | Initializer Agent | AI 根据 spec.md 生成 |
| **开发模式** | Agent 自动编码 | AI 辅助 + 人工编码 |
| **测试方式** | Agent 自动测试 | /pep-test 触发测试 |
| **状态管理** | feature_list.json + progress notes | features.json + session_state + archive |
| **适用场景** | 实验性、完全自动化 | 生产环境、人机协作 |

### 为什么选择 AI-First 而非全自动？

1. **生产环境需要控制**
   - 代码质量需要人工把关
   - 关键决策需要人工参与
   - 避免 AI "跑偏"

2. **灵活性更高**
   - 可以随时介入
   - 可以调整方向
   - 可以跳过某些步骤

3. **学习和积累**
   - 开发者参与过程
   - 积累经验和知识
   - 形成团队规范

4. **渐进式规格**
   - spec.md 可以逐步完善
   - 不需要一开始就完美
   - 支持敏捷开发

## 💡 最佳实践

### 1. 先写 spec.md，再生成任务

```markdown
❌ 不推荐:
直接开始编码 → 功能蔓延 → 难以收敛

✅ 推荐:
完善 spec.md → 生成任务 → 按任务实施 → 可控推进
```

### 2. 保持任务粒度合理

```markdown
❌ 太大:
"实现整个组件" → 难以完成 → 容易放弃

❌ 太小:
"添加一个变量" → 过度琐碎 → 效率低下

✅ 合适:
"实现轮播逻辑" → 2-4 小时 → 成就感强
```

### 3. 及时完成和提交

```markdown
✅ 完成一个任务，立即:
• 运行 /pep-done
• 提交代码
• 归档任务
• 开始下一个

❌ 避免:
• 同时进行多个任务
• 积累大量未提交代码
• 忘记标记完成
```

### 4. 定期运行 /pep-check

```markdown
✅ 建议在以下情况检查:
• 长时间中断后
• 感觉状态不对时
• 准备开始新任务前
• 遇到问题时

AI 会诊断状态并提供修复建议
```

### 5. 利用 /pep-test 保证质量

```markdown
✅ 建议测试时机:
• 核心功能完成后
• UI 实现完成后
• 准备发布前

不要等到最后才测试！
```

## 🎯 总结

PEP 组件 AI-First 开发流程：

1. **以 AI 为主导**: 通过 Commands 与 AI 对话
2. **以规格为驱动**: spec.md 驱动任务生成
3. **以任务为单元**: 逐个任务推进
4. **以状态为基础**: 智能检测，避免混乱
5. **以测试为保障**: 自动化测试，质量可控

这是一个**人机协作**的开发流程，而不是完全自动化，更适合真实的生产环境。
