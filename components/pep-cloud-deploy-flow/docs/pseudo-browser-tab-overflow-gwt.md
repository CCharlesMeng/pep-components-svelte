# PseudoBrowser Tab Overflow Logic

本文说明 `pep-cloud-deploy-flow` 中伪浏览器 header 的 tab 响应式压缩、固定新增按钮、箭头滚动与边界行为。

相关实现文件：

- `src/components/PseudoBrowser.svelte`
- `src/utils/pseudo-browser-tab-overflow.ts`
- `src/utils/pseudo-browser-tab-scroll.ts`

## 目标

该逻辑的目标不是单纯“让 tab 能滚动”，而是分阶段保证以下体验：

- tab 数量较少时，新增按钮紧跟最后一个 tab。
- tab 数量增多时，优先压缩每个 tab，而不是立刻进入滚动。
- 压缩阶段要保证所有 tab 仍然都在可视区域内。
- 只有当 tab 压缩到 `70px` 后仍放不下，才出现左右箭头并进入横向滚动。
- 新增按钮与右侧全屏/切回按钮始终保留独立可点击区域。

## 宽度规则

- tab 最大宽度：`166px`
- tab 最小宽度：`70px`
- tab 间距：`2px`
- tab 最大数量：`30`
- 固定新增按钮模式下，为按钮与右侧工具区预留的 tab 主区宽度：`48px`
- 出现左右箭头后，箭头总预留宽度：`46px`

## Given / When / Then

### 场景 1：tab 数量较少，未触发压缩

**Given**

- 当前 tab 数量较少。
- tab 主区可用宽度足以让每个 tab 保持 `166px`。
- 新增按钮可以自然跟在最后一个 tab 后面。

**When**

- 用户首次打开伪浏览器。
- 或用户新增 tab 后，所有 tab 仍能以 `166px` 宽度完整显示。

**Then**

- 每个 tab 保持最大宽度 `166px`。
- 新增按钮出现在轨道内部，并紧跟最后一个 tab。
- 不显示左右箭头。
- `tabs-viewport` 不启用横向滚动。
- 当前 active tab 不需要额外滚动定位，因为所有 tab 都在可视区域内。

### 场景 2：tab 数量增多，进入压缩阶段

**Given**

- tab 数量继续增加。
- 如果仍让新增按钮跟在最后一个 tab 后面，tab 轨道会开始逼近可视边界。
- 但当前还没有达到“70px 也放不下”的程度。

**When**

- 宽度计算结果显示 tab 已不能继续维持 `166px`。
- 但按压缩计算后，tab 仍可在 `70px ~ 166px` 之间完整容纳。

**Then**

- 新增按钮从“跟随最后一个 tab”切换为“固定在右侧工具区前”。
- tab 主区开始按剩余可用宽度等比压缩。
- 所有 tab 仍然必须处于可视区域内。
- 不显示左右箭头。
- 不启用横向滚动。
- 新增 tab 后，新的 active tab 应该仍然可见，因为此阶段是“压缩适配”而不是“滚动适配”。

### 场景 3：tab 压缩到最小宽度后仍放不下

**Given**

- tab 已经进入压缩阶段。
- 每个 tab 已经压缩到 `70px`。
- 即使保持 `70px`，所有 tab 仍然无法放入当前可用宽度。

**When**

- 宽度计算结果判定 `idealWidth < 70`。

**Then**

- 组件切换到横向滚动模式。
- 左右箭头出现。
- 新增按钮继续固定在右侧工具区前。
- tab 使用固定宽度渲染，并以横向轨道形式排列。
- `tabs-viewport` 开启 `overflow-x: auto`。

### 场景 4：滚动模式下新增 tab

**Given**

- 当前已经处于横向滚动模式。
- 右侧会显示新增按钮与工具按钮。
- 新增 tab 会出现在轨道最右侧。

**When**

- 用户点击新增 tab。

**Then**

- 新建 tab 会立即成为 active tab。
- 新增后组件会在布局完成后自动滚动到最右侧。
- 新 active tab 必须进入可视区域。
- 如果此前正处于临界点，新增动作导致首次进入滚动模式，也必须在切换完成后自动滚动到 active tab。

### 场景 5：点击左右箭头

**Given**

- 当前已进入滚动模式。
- 轨道内容超过可视区域。

**When**

- 用户点击左箭头或右箭头。

**Then**

- 每次点击滚动一个 tab 宽度。
- 左箭头负责向左滚动。
- 右箭头负责向右滚动。
- 滚动后会重新计算当前是否还能继续向左或向右。

### 场景 6：长按左右箭头

**Given**

- 当前已进入滚动模式。
- 箭头对应方向仍有剩余可滚动距离。

**When**

- 用户按住某个方向箭头不放。

**Then**

- 组件会连续滚动。
- 连续滚动从较慢速度开始。
- 随着按住时间增加，滚动频率逐步加快。
- 到达边界时自动停止。

### 场景 7：到达滚动边界

**Given**

- 当前已进入滚动模式。
- 轨道已经滚动到最左侧或最右侧。

**When**

- 组件更新滚动边界状态。

**Then**

- 若在最左侧，则左箭头为禁用态。
- 若在最右侧，则右箭头为禁用态。
- 禁用态箭头使用灰色资源图。
- 对应方向不应再继续触发有效滚动。

### 场景 8：超过最大 tab 数量

**Given**

- 当前 tab 数量已经达到 `30`。

**When**

- 用户继续点击新增 tab。
- 或外部链接接管逻辑尝试继续注入 tab。

**Then**

- 不会继续新增 tab。
- 在页面右上角显示 warning 弹窗提示用户（距离上/右 `16px`）。
- 提示标题为：`告警信息`。
- 提示文案为：`页签已增加至最大数量，如需继续增加可关闭无用标签`。
- 弹窗默认展示 `3s` 后自动关闭。
- 在弹窗展示期间频繁触发告警不会重复渲染，仅保持当前弹窗展示直至自动关闭或手动关闭。

### 场景 9：tab 宽度计算的边界一致性

**Given**

- tab 宽度规则来自 `pseudo-browser-tab-overflow.ts`。
- 实际 tab 样式包含左右 padding。

**When**

- 组件判断是否已经到达 `70px` 临界点。

**Then**

- tab 元素必须使用 `box-sizing: border-box`。
- 这样 `70px` 与 `166px` 表示的是 tab 的最终占位宽度，而不是仅内容区宽度。
- 计算结果与页面真实渲染宽度保持一致。
- 避免出现“逻辑上应该滚动，但页面实际上已经被遮挡”的误判。

## 阶段切换摘要

可以把 header 理解为 3 个阶段：

1. 跟随阶段  
   tab 固定最大宽度，新增按钮跟在最后一个 tab 后面。

2. 压缩阶段  
   新增按钮固定到右侧，tab 在 `70px ~ 166px` 之间自适应压缩，所有 tab 仍可见。

3. 滚动阶段  
   tab 已压到 `70px` 仍不足以容纳全部内容，于是出现左右箭头，启用横向滚动，并自动保证 active tab 可见。

## 代码职责划分

### `src/utils/pseudo-browser-tab-overflow.ts`

负责纯计算：

- 最大/最小 tab 宽度
- tab 轨道总宽度
- 当前是否已进入压缩阶段
- 当前是否必须进入滚动阶段

### `src/utils/pseudo-browser-tab-scroll.ts`

负责交互控制：

- 单次点击滚动一个 tab
- 长按连续滚动
- 加速节奏
- 左右边界状态

### `src/components/PseudoBrowser.svelte`

负责视图和状态接入：

- 根据当前阶段决定新增按钮是在轨道内部还是固定在右侧
- 根据当前阶段决定是否显示箭头
- 在滚动阶段自动保证 active tab 可见
- 对新增、关闭、切换 tab 后的布局进行重算

## 验收建议

建议按下面顺序人工验证：

1. 从 1 个 tab 开始连续新增，观察“跟随阶段 -> 压缩阶段 -> 滚动阶段”的切换是否符合预期。
2. 在压缩阶段确认所有 tab 都仍然可见，最后一个 tab 不被新增按钮遮挡。
3. 在首次进入滚动阶段时确认左右箭头立即出现。
4. 在滚动阶段新增 tab，确认会自动滚到最右侧并看到新 active tab。
5. 连续长按左右箭头，确认会加速并在边界停止。
6. 新增到 30 个后继续新增，确认弹出占位提示且不再新增。
