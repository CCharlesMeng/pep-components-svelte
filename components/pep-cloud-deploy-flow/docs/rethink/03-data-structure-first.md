# 数据结构先行的重要性

## 这是最大的教训之一

从对话历史看，schema.json 经历了多次重大重构：

| 变更 | 影响 |
|------|------|
| `$ref` → 内联 | 简化了 schema 可读性，但导致类型定义要跟着改 |
| `oneOf` → 移除 | 降低了 schema 复杂度，但要在 resolver 里做兼容 |
| `linkWhitelist` + `domainWhitelist` → 合并 | 更合理，但组件里的引用全要换 |
| `tabs` 结构收敛 | 统一了单应用/多应用的数据模型 |
| `shortcuts` 三处集中配置 | 运营视角更好，但需要 `props-resolver.ts` 做运行时合并 |
| `mobile.steps` 继承逻辑 | 减少了运营配置量，但增加了 `resolveMobileSteps` 的隐式逻辑 |

**每次 schema 变一次，组件可能要改三个文件。**

## 理想方式

在写任何组件代码之前，先花 1-2 轮对话**只讨论数据结构**：

1. 给出一份「运营人员会填什么数据」的表格，AI 来设计 schema，人来审核
2. 明确区分三种数据的边界：

| 数据类型 | 来源 | 示例 |
|---------|------|------|
| 编配时数据 | 运营在后台填的 | 步骤标题、Logo URL、品牌色 |
| 运行时数据 | 服务端 preload 的 | htmlUrl 内容预取、远程 CSS |
| 衍生数据 | 前端计算的 | sidebar 当前宽度、当前步骤索引 |

现在的 `props-resolver.ts` 做的合并工作，其实反映了这三者边界在开发过程中是模糊的。

## Schema 设计：运营友好 vs 开发友好的矛盾

Schema 最终是要给运营填的。但开发过程中，schema 的演进是**开发驱动**的（"我需要这个字段"），而非**运营驱动**的（"运营能理解这个字段吗"）。

**如果再来一次**：先列出运营需要配置的所有「业务概念」（云产品列表、步骤指引、品牌色等），再映射到技术字段。而不是从技术结构出发倒推运营表单。
