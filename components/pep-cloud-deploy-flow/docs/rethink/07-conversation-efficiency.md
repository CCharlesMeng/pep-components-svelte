# 对话效率与协作节奏

## 对话分类统计

从 75+ 轮对话来看，可以大致分类：

| 类型 | 约占比 | 示例 |
|------|--------|------|
| 功能开发 | ~35% | sidebar 布局、伪浏览器、移动端、远程内容 |
| Bug 修复 / 细节调整 | ~25% | resize 拖拽、tooltip 偏移、scrollbar、margin |
| Schema / 数据结构重构 | ~15% | $ref 移除、oneOf 移除、字段合并、shortcuts 集中 |
| Git 提交/推送 | ~13% | 至少 10 次单独的提交推送对话 |
| 设计对齐 / 视觉调整 | ~8% | 1:1 对比、像素级修复、图标替换 |
| 技能/工具讨论 | ~4% | Skill 评估、对比截图 Skill |

## 效率浪费点

### 1. Git 操作过于碎片化

~10 次独立的"提交并推送"对话。每次都是一轮完整的上下文建立。

**改进**：可以设定节奏——每完成一个完整功能模块后统一提交，而非每次小改动都单独开对话推送。

### 2. Schema 反复修改

如果前置设计到位，以下对话本可避免：

- 去掉 `$ref` 改回内联
- 去掉 `oneOf` 重设计
- `linkWhitelist` 与 `domainWhitelist` 合并
- schema 与 default.json 对齐
- schema 运营可填性优化

**改进**：1-2 轮专门的 schema 设计对话 → 定稿 → 再开发。

### 3. 单一样式微调

scrollbar、`body` 默认 `margin:8px`、hover 高度铺满等——每个都是一次对话。

**改进**：攒批处理。收集一个"视觉微调清单"，一次性对话处理。

### 4. 架构决策的推翻成本

sidebar 左→右迁移是最典型的例子。这不是一个小改动——它影响了 tooltip 定位、snap shadow、resize handle、浮动面板贴边方向等多个子系统。

**改进**：关键的布局决策（sidebar 在哪一侧、有哪些状态）应该在第一天通过状态机图等方式锁定。

### 5. 还原设计稿时缺少组件库意识

一开始直接还原设计稿的 button，后来发现各处按钮风格不一。如果先花 0.5 轮对话做"UI 原子审计"，后续所有组件开发都能基于一致的基础。

## 理想的对话节奏

```
第 1 轮：  全局信息架构 + 使用场景 + 技术约束
第 2 轮：  数据结构设计（schema.json + types.ts）
第 3 轮：  UI 原子审计 → 基础组件开发（Button、Tab、Tooltip、Icon、Loading）
第 4 轮：  PC 骨架布局 + 状态机
第 5-7 轮：PC 各模块实现（sidebar → browser → main → deployment flow）
第 8 轮：  PC 细节打磨 + 1:1 设计对比
第 9 轮：  移动端开发
第 10 轮： 远程内容子系统集成测试
第 11 轮： 最终打磨 + 提交
```

**对比现在 75+ 轮，理论上可以压缩到 15-20 轮高质量对话。**

## 对 AI 协作的特别建议

### 给 AI 的初始 prompt 应包含

1. **完整的设计稿集合**（所有状态、所有端）
2. **数据模型草案**或至少是业务概念列表
3. **不变量清单**：哪些决策是锁定的
4. **已有的代码约定**：同项目其他组件的样式

### 对话中的最佳实践

1. **批量提需求**：多个小调整合成一次对话
2. **前置审核**：AI 提出数据结构/架构方案 → 人审核确认 → 再实现
3. **明确的优先级**：告诉 AI 先做什么后做什么，而非让 AI 按设计稿顺序还原
4. **组件库意识**：第一次看到重复模式时就提出"需要提取为共享组件"

### 减少返工的信号

如果在对话中出现以下信号，说明流程可能出了问题：
- "把 sidebar 从左边移到右边" → 关键决策没有前置锁定
- "schema 里的 oneOf 去掉" → 数据结构设计不充分
- "这个按钮样式和那边不一样" → 缺少组件库
- "移动端的步骤数据为什么是 8 步" → 数据继承逻辑不透明
