# 核心教训总结

## 一句话概括每个教训

| # | 教训 | 典型反面案例 |
|---|------|-------------|
| 1 | **数据结构先行** — schema 变一次，组件可能要改三个文件 | schema.json 经历了 $ref→内联、oneOf→移除、字段合并等 6+ 次重构 |
| 2 | **全局视野先于像素精度** — 先把所有状态和模块列清楚，再看设计稿 | 设计稿逐步透露导致 sidebar 左→右大迁移 |
| 3 | **不变量要早期锁定** — sidebar 在哪一侧、有哪些状态，应该是第一天的决策 | sidebar 左右迁移影响了 5+ 个子系统 |
| 4 | **移动端是子集而非分支** — 数据层应该统一，渲染层分离 | mobile.steps 的隐式继承增加了理解成本和 bug 概率 |
| 5 | **技术子系统独立验证** — 远程内容加载、Shadow DOM 等应先做 POC | 远程内容系统在 sidebar 开发中逐步搭建，反复调整 |
| 6 | **组件库意识前置** — 先识别 UI 原子，再开发业务组件 | button 各处不一致，tab、tooltip、loading 各写各的 |
| 7 | **对话要有节奏** — 设计→结构→实现→打磨，而非螺旋式发散 | 75+ 轮对话，其中 ~13% 是单独的 git push |
| 8 | **批量处理琐碎事务** — git push、样式微调不需要每次单独对话 | scrollbar、margin:8px、hover 高度各占一次对话 |

## 理想开发流程 vs 实际流程

### 实际流程（螺旋式）

```
设计稿 → button 开发 → 发现不一致 → 重写 button
  → sidebar 开发 → 左侧 → 改右侧 → resize 问题 → 修 ×4
    → schema 设计 → 改 $ref → 改 oneOf → 改字段名
      → 移动端开发 → 步骤继承问题 → 修数据层
        → 远程内容 → Shadow DOM → 缓存 → 作用域
          → 细节打磨 → git push → 细节 → git push → ...
```

### 理想流程（瀑布+迭代）

```
Phase 1 - 设计（2 轮）
├── 全局信息架构
├── 数据结构定稿
└── UI 原子审计

Phase 2 - 基础（2 轮）
├── types.ts + schema.json
└── 原子组件（Button, Tab, Tooltip, Icon, Loading, StepBar）

Phase 3 - PC 端（4-5 轮）
├── 骨架布局 + 状态机
├── Sidebar（右侧，状态机驱动）
├── PseudoBrowser（功能清单驱动）
├── MainPanel + DeploymentFinished
└── 远程内容子系统（独立 POC → 集成）

Phase 4 - 移动端（1-2 轮）
├── MobileFlow（基于 PC 数据子集）
└── 移动端特有交互

Phase 5 - 打磨（2-3 轮）
├── 1:1 设计对比
├── 批量视觉微调
└── 测试 + 最终提交
```

**预计轮次：15-20 轮 vs 实际 75+ 轮。效率提升约 4 倍。**

## 适用范围

这些教训不仅适用于 pep-cloud-deploy-flow，对同类「配置驱动的复杂交互组件」开发都有参考价值：

- 任何有 schema.json 驱动的可配置组件
- 需要同时支持 PC 和移动端的组件
- 包含复杂布局状态（resize、collapse、float）的组件
- 涉及远程内容加载和渲染隔离的组件
- AI 辅助开发的多轮对话场景
